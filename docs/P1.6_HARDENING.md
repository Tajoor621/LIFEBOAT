## 1. Reproducible builds

The Rust workspace and Docker build use `--locked`. On the first CI run in a repository without `Cargo.lock`, CI generates the lockfile, runs all validation gates against that exact resolution, and commits the lockfile directly to `main` only if every gate passes. Subsequent builds refuse to resolve dependency changes implicitly.

## 2. Credential file, enrollment, rotation and revocation

The service reads a version-1 JSON file from `LIFEBOAT_CREDENTIALS_FILE` (default `/etc/lifeboat/credentials.json`). The file contains BLAKE3 token digests, never raw bearer tokens. On Unix it must have permissions `0600` or stricter. Mount it read-only into the container and ensure its owner can read it as UID 10001.

Example structure: [credentials.example.json](../config/credentials.example.json). Replace the example digest before use; the all-zero value is intentionally not a usable token.

Generate a high-entropy token outside the service and pipe it to the helper so it is not placed in command arguments:

```sh
TOKEN="$(openssl rand -hex 32)"
printf '%s' "$TOKEN" | docker run --rm -i --entrypoint /usr/local/bin/lifeboat-vault lifeboat-vault:local credential-hash 00112233445566778899aabbccddeeff
```

The helper prints only the BLAKE3 digest. Store the raw token only in the authorized client’s secret storage; do not place it in shell history, logs, tickets, or the credentials file.

### Rotation

1. Generate a new random token and calculate its digest with the helper.
2. In the credentials file, set the new digest as `active_token_blake3`, move the old active digest to `previous_token_blake3`, and set `previous_valid_until_unix` to a short UTC Unix-time deadline (recommended maximum 10 minutes).
3. Deliver the new raw token securely to the owner-authorized client and restart the service after installing the updated file.
4. After the deadline, remove both previous-token fields and restart. The old token is then rejected.
5. To revoke immediately, remove the device entry or remove its previous digest and restart. Revocation is effective after the service reload/restart; this phase does not provide online hot reload.

A previous digest without an expiry, or an expiry without a previous digest, is rejected. Duplicate device IDs, malformed hashes, unsupported versions, and insecure Unix file permissions fail startup.

### Device enrollment

Create a new device entry with a unique 32-character lowercase hexadecimal device ID and a freshly generated token digest. Deliver the raw token only to that owner-authorized device. Restart the service to load the entry. There is deliberately no public enrollment endpoint.

## 3. Request resource limits

Body limits are applied at the route boundary before Axum extracts request bodies:
- Encrypted object PUT: 16 MiB + 16 bytes (ciphertext envelope allowance).
- Encrypted manifest PUT: 8 MiB.
- Resumable-upload session JSON: 4 KiB.
- Resumable-upload chunk PUT: 1 MiB.

Authentication middleware still runs before the handler extracts the body. Rejected oversized bodies must not create storage objects, upload sessions, or quota reservations.

## 4. Audit ledger

Security-relevant successful writes append JSONL records to `<vault-root>/audit/events.jsonl`. Each record includes a monotonically increasing sequence, timestamp, device ID, action, opaque resource ID, outcome, previous record hash, and its own BLAKE3 hash. No bearer token, encryption key, or plaintext content is recorded.

The ledger is verified at startup; malformed, missing, reordered, or modified records cause the service to fail closed. Appends are synchronized before the API reports success. This is tamper-evident, not tamper-proof: a privileged attacker able to rewrite the entire file can recompute the chain. Production deployments should periodically export/anchor signed ledger checkpoints to an independently controlled system. Ledger retention and deletion must be managed as sensitive operational data.

## 5. Network and container boundary

The application defaults to `127.0.0.1:8080`. The Docker image intentionally does not override that safe default. To make the container reachable through a published port, explicitly set `LIFEBOAT_BIND=0.0.0.0:8080` and put it behind a TLS-terminating reverse proxy and firewall. Do not publish the raw HTTP port directly to the public Internet. The API itself does not terminate TLS.

Example runtime requirements:
- Mount a persistent vault volume at `/var/lib/lifeboat/vault`.
- Mount credentials read-only at `/etc/lifeboat/credentials.json`.
- Bind the service only to a private container network behind a TLS proxy.
- Back up the encrypted vault volume and audit ledger independently.
- Restrict host access to the volume and credential file; container non-root UID is 10001.
- Keep single-process deployment only. Rate limits, storage serialization and audit mutex are process-local.

## 6. Validation

CI gates:
- `cargo fmt --all -- --check`
- `cargo test --locked --workspace --all-targets`
- `cargo clippy --locked --workspace --all-targets -- -D warnings`
- `cargo build --locked --workspace --release`
- Docker image build and container smoke test for health and unauthenticated API rejection.

Focused tests cover credential rotation expiry, manifest body limits, audit restart verification and audit tamper detection. The operator must still perform a deployment smoke test, restart an interrupted upload, verify restore from an independent copy, test disk-full/permission-denied behavior, and arrange an independent security review before any public deployment or production use.

## Explicit limitations

- No online token enrollment, hot reload, or remote revocation; changes require a controlled service restart.
- No multi-node consistency or distributed rate limiting.
- No TLS termination in the vault process.
- No audit checkpoint anchoring yet.
- No production Android client, desktop console, cloud connectors, or end-to-end phone restore workflow.
- No destructive remote wipe behavior.
