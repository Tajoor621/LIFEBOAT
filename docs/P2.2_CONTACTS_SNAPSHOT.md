# P2.2 — Owner-initiated Contacts snapshot

## Delivered scope

- The manifest declares only `READ_CONTACTS`; no network permission or background component is present.
- Permission is requested only after the owner saves explicit Contacts consent and presses **Connect Contacts and export VCF**.
- The Contacts Provider is queried read-only. LIFEBOAT does not add, edit, delete, or sync contacts.
- The VCF 4.0 UTF-8 writer supports structured names, phone numbers, email addresses, organizations/titles, and postal-address text.
- Provider rows are consumed in contact-ID order and serialized one contact at a time. Personal data is never written to logs.
- The owner chooses the destination using Android's document picker. Temporary VCF staging is app-private and deleted after export, cancellation, or failure.
- A private JSON evidence record stores export time, byte count, SHA-256, and completion state without contact values. Provider count, exported vCard count, and row count are shown in the app's completion summary.

## Permission and failure behavior

- No permission request on install, launch, or consent save.
- No provider query without a current READ_CONTACTS grant.
- Denial is recorded as denied; a subsequent denial after a prior request with no rationale is treated as permanently denied.
- Permission is rechecked during provider-row processing and after the query. Provider errors or revocation delete the incomplete staging file and are reported as failure.

## Boundaries and limitations

- No upload, encryption integration, background scheduling, remote access, contact modification, or cloud account access is implemented.
- This VCF is a portable contacts export, not a complete phone backup and not proof every provider/account-specific field is represented.
- Provider-reported contacts and exported vCards are separate counts; any mismatch must remain visible and cannot be described as full coverage.
- Large-address-book and permission-revocation behavior requires real-device testing. JVM tests validate VCF text encoding, not Android provider behavior.
