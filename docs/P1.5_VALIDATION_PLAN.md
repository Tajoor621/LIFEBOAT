# P1.5 — Integration, failure recovery and security validation

Status: automated CI gates passed on main commit `863474b4bee82b99987abf33992fab431d888d47`; manual release validation and independent security review remain pending.

P1.5 is a verification phase, not a claim that the vault is production-ready. Tests must run in CI before P1.5 can be accepted.

## Automated coverage added in this phase

- API test roots are unique per test process/test invocation to prevent shared filesystem state from causing cross-test interference.
- The authenticated API round-trip now asserts that immutable object IDs cannot be overwritten.
- A rate-limit test makes 120 authenticated requests in one window and expects request 121 to return HTTP 429.
- The restore core now has a multi-chunk contact fixture that checks exact reassembly order and format validation.
- CI builds the actual container image after Rust format, test, and Clippy checks. This catches drift between the Rust workspace and Docker build definition.

## Required CI gates

Run the workflow on the exact main commit under review and require all steps to pass:

1. cargo fmt --all -- --check
2. cargo test --workspace --all-targets
3. cargo clippy --workspace --all-targets -- -D warnings
4. docker build -t lifeboat-vault:ci .

A missing status is not a pass. The four gates above passed together on commit `863474b4bee82b99987abf33992fab431d888d47` in [GitHub Actions run 44730376308](https://github.com/Tajoor621/LIFEBOAT/actions/runs/44730376308). A green CI run is not an independent security review.

## Failure and abuse test matrix

| Scenario | Expected safe result |
|---|---|
| Wrong bearer token / unknown device | 401; no data returned |
| Cross-device URL substitution | 401; no cross-namespace access |
| 121st request within a device window | 429 |
| Duplicate immutable object PUT | 409; original bytes remain unchanged |
| Wrong chunk digest | Rejected; no receipt recorded |
| Conflicting retry for acknowledged chunk | Rejected; acknowledged bytes unchanged |
| Incomplete upload completion | Rejected; object not committed |
| Restart during upload | Persisted acknowledged chunks remain resumable |
| Lost completion response | Retried completion returns verified receipt |
| Truncated or altered stored object | Digest/integrity failure; no bytes accepted as verified |
| Wrong passphrase or altered recovery code | Unlock fails |
| Altered vault ID / wrapping slot | Authenticated decryption fails |
| Damaged passphrase KDF metadata | Passphrase unlock fails; independent recovery-code path remains available if its envelope and wrapper structure are intact |
| Missing or reordered restore chunk | Rehearsal fails and removes its scratch outputs |
| Parser rejects restored item | Rehearsal fails and removes its scratch outputs |
| Restore sample succeeds | Only selected items are reported verified; no claim of complete snapshot coverage |

## Manual release checks

These require an operator/deployment environment and must be recorded separately from CI:

- Start a fresh vault with newly generated high-entropy device credentials.
- Confirm the service binds to loopback in the documented Compose deployment.
- Confirm no credential appears in logs, process output, repository history, or API responses.
- Upload a representative encrypted object, restart the container, then retrieve it with its expected digest.
- Interrupt an upload between chunks, restart the service, and resume only missing chunks.
- Attempt a wrong-device token and confirm no data is disclosed.
- Restore a real VCF export with a real VCF parser, and at least one media/document item with its real format validator.
- Perform a clean-environment recovery drill using only the offline Recovery Kit and separately stored encrypted backup.
- Verify that the restored data opens and that source metadata/relationships are preserved by the restore application.
- Review filesystem permissions, backup volume permissions, TLS reverse-proxy configuration, host firewall, secret storage, monitoring and incident response.

## Known blockers — do not waive

- No committed Cargo.lock yet; dependency resolution is not yet reproducible across time.
- No online device-token rotation/revocation or durable device enrollment.
- Rate limits and write serialization are process-local; no multi-node safety.
- No durable tamper-evident audit ledger.
- No committed-object retention/deletion policy or S3 backend.
- No network fuzzing, independent cryptographic review, or deployment penetration test.
- No production client orchestration, complete per-format validators, QR/PDF Recovery Kit UI, or clean-machine cross-device restore proof.

## Exit criteria

The automated P1.5 CI gate is satisfied on the commit cited above. P1.5 as a whole remains open until manual checks are recorded and the remaining security blockers have an explicit owner and mitigation plan. Do not expose this service to the public Internet or store irreplaceable data as its only copy before these conditions are met.
